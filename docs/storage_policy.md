# Storage Policy & Manifest Specification

- **Target Architecture**: Hexagonal Universal Storage Policy
- **Author**: Antigravity AI & LatentMAS Core Team
- **Version**: 1.0.0
- **Status**: Implemented (`ref/storage-policy`)

---

## 1. Storage Tiers & Lifecycle Contracts

All experiment outputs and assets adhere to four distinct lifecycle tiers:

| Tier | Directory | Retention Class | Cleanable via `clean-cache`? | Description |
| :--- | :--- | :--- | :--- | :--- |
| **Tier 1: Research Storage** | `storage/` | `persistent` | **NEVER** | SQLite tracking DB (`storage/mlflow/mlflow.db`), MLflow artifacts (`storage/mlflow/mlflow_artifacts/`), and heavy tensor store (`storage/tensors/`). |
| **Tier 2: Publication Artifacts** | `artifacts/` | `persistent` | **NEVER** | Presentation figures (PNG/PDF 300dpi), final analysis summaries, and condition CSV tables. |
| **Tier 3: Execution Cache** | `.cache/` | `temporary` / `regenerable` | **YES (Safe)** | Reconstructable model projection matrices (`models/realign/`), intermediate sample logs, and runtime scratchpads. |
| **Tier 4: Dataset Files** | `data/` | `persistent` | **NEVER** | Immutable benchmark data (e.g., `data/medqa.json`). |

## 2. Identifier Separation & Contracts

To eliminate collisions across runs, configurations, and models, the storage policy strictly separates five identifiers:

```
[config_id]   ──────▶ Deterministic hash/string of experimental hyper-parameters
    │
    ▼
 [run_id]     ──────▶ Unique MLflow Run UUID (e.g. "a1b2c3d4...") identifying one concrete execution
    │
    ├─── [sample_key]  ──────▶ SHA-256 hash prefix identifying problem prompt across datasets/splits
    │
    ├─── [branch_id]   ──────▶ Experimental condition or intervention arm ("own", "cross", "drop", "zero")
    │
    └─── [artifact_id] ──────▶ Specific tensor or data object name ("hidden_state_step_10", "pre_branch_kv")
```

### Identifier Definitions:
1. **`config_id`**: Generated via `build_run_id()`. Deterministic across equivalent hyperparameters. Logged as a tag and parameter in MLflow.
2. **`run_id`**: Generated by `MLflowTracker.start_run()`. Unique to each invocation. Isolates file paths in `storage/tensors/{run_id}/`.
3. **`sample_key`**: Generated via `compute_sample_key(task, split, question)`. Format: `sha256(f"{task}:{split}:{question}".encode()).hexdigest()[:16]`.
4. **`branch_id`**: Identifies reasoning condition (e.g., `common`, `own`, `cross`, `drop`, `zero`).
5. **`artifact_id`**: Unique identifier for an artifact within a run (e.g., `kv_snapshot`, `sender_states`).

## 3. Universal Tensor Store & Manifest Schema

Heavy tensors (such as KV snapshots and hidden state trajectories) are persisted in `storage/tensors/{run_id}/` and indexed by a lightweight `tensor_manifest.json`.

### 3.1 Manifest JSON Schema (`tensor_manifest.json`)
```json
{
  "run_id": "a1b2c3d4e5f67890",
  "schema_version": "1.0.0",
  "created_at": "2026-10-23T09:30:00.000000+00:00",
  "updated_at": "2026-10-23T09:35:12.000000+00:00",
  "entries": {
    "kv_snapshot_branch_own": {
      "run_id": "a1b2c3d4e5f67890",
      "sample_key": "7f83b1657ff1fc53",
      "branch_id": "own",
      "segment_id": "0",
      "artifact_id": "kv_snapshot_branch_own",
      "artifact_type": "kv_snapshot",
      "storage_uri": "file:///path/to/storage/tensors/a1b2c3d4e5f67890/kv_snapshot_branch_own.pt",
      "shape": [2, 32, 16, 512, 128],
      "dtype": "torch.bfloat16",
      "checksum": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "schema_version": "1.0.0",
      "retention_class": "persistent",
      "status": "complete",
      "created_at": "2026-10-23T09:35:10.000000+00:00",
      "metadata": {
        "step": 20,
        "token_count": 512
      }
    }
  }
}
```

### 3.2 Integrity and Durability Guarantees:
1. **Atomic File Writing**: Tensors are written to a hidden temporary file (`.{artifact_id}.pt.tmp`) and atomically renamed upon successful completion and checksum computation.
2. **Atomic Manifest Update**: The manifest is serialized to `tensor_manifest.json.tmp` and atomically replaced.
3. **Checksum Validation**: On loading, if `verify_checksum=True` (default), the SHA-256 of the on-disk file is verified. Mismatches raise a `ValueError` and flag the entry status as `corrupted`.
4. **Missing File Detection**: If the file was moved or deleted, loading raises `FileNotFoundError` and flags the status as `missing`.
5. **Zero-Copy Cross-Branch Referencing**: When branching (e.g., in PLCE/PLPE experiments), common pre-branch KV snapshots are referenced via `register_reference()`, pointing to the same immutable storage URI and checksum without disk duplication.

## 4. Crash-Safe and Incremental Storage Policy

1. **Incremental JSONL Logging**:
   - `BenchmarkUseCase`: Appends completed problem results to `samples.jsonl` after every batch. Re-execution automatically resumes from completed sample keys.
   - `ReceiverAcquisitionUseCase`: Appends evaluated carrier digit records to `runtime/acquisition_partial_*.jsonl` on every sample.
   - `InterventionUseCase`: Appends evaluated condition records to `runtime/intervention_partial_*.jsonl` on every sample.
2. **No Silent Exception Suppression**:
   - All critical I/O operations are wrapped with explicit error logging (`logger.error`).
   - Failure to save evaluation caches or run summaries marks the run as `FAILED` rather than silently exiting with code 0.
3. **Safe Cache Cleanup & Resumption Protection**:
   - `just clean-cache` executes `ExecutionCacheManager.clean_volatile_cache()`.
   - **Protection of In-progress Experiments**: Active benchmark runs with `samples.jsonl` (resumption state not yet finalized or uploaded to MLflow) in `evaluation/runs` are **strictly protected** by default (`include_resumable_runs=False`). Even when `include_resumable_runs=True` is provided, incomplete runs missing `summary.json` are retained unless `purge_incomplete_runs=True` is explicitly specified.
   - Strictly validates with `PathResolver.is_safe_cache_path()` to ensure that `storage/`, `artifacts/`, `configs/`, and `data/` are never touched.

## 5. Strict Data Reader Isolation & Fallback Policy

To prevent false successes and cross-run data corruption during post-hoc analysis:
1. **Run-Scoped Artifact Loading**: `ResearchDataReader.load_artifact(run_id, artifact_path)` strictly queries MLflow for `run_id`, or checks run-scoped directories (`storage/{run_id}/`, `.cache/evaluation/runs/{run_id}/`, `artifacts/{run_id}/`).
2. **Unscoped Fallback Blocked by Default**: If an artifact or tensor file is found at a global/legacy path (e.g. `artifacts/summary.json` or `.cache/.../sender_latent_states.pt`), it is **strictly rejected** unless:
   - For JSON files: the file content contains a verified matching `"run_id"` or `"mlflow_run_id"`. (`config_id` cannot be used to verify run-level provenance because multiple executions share identical configs).
   - For other artifacts/tensors: the caller explicitly passes `allow_unscoped_fallback=True`.
3. **Provenance Auditing**: Every retrieved artifact records its source origin (`provenance`), ensuring traceability back to the concrete MLflow Run ID.

## 6. Intervention KV Cache Isolation & Content-Based Sample Key

To eliminate collisions when exploring different prompts, model revisions, sampling configurations, or sample subsets:
1. **Deterministic Config Fingerprint**: `build_intervention_config_id(args, model_dtype)` computes a full `config_id` and a 12-char SHA-256 `config_hash` incorporating `model_name`, `revision`, `task`, `split`, `prompt`, `latent_steps`, `seed`, `temperature`, `top_p`, `backend`, and `dtype`.
2. **Content-Based Sample Key**: Instead of relying on volatile loop indices (`idx`) which shift when dataset order or sample slices change, cache keys incorporate `sample_key = compute_sample_key(task, split, question)[:16]`.
3. **Isolated Cache Keys**: Raw latent contexts are saved as `latent_{task}_{model_slug}_cfg{config_hash}_key_{sample_key[:16]}_s{seed}.pt`. Legacy aliases `latent_{task}_{idx}_s{seed}.pt` are maintained concurrently for backward compatibility.
4. **MLflow Tagging**: Both `config_id` and `config_hash` are logged as tags and parameters in MLflow.

## 7. Legacy MLflow Path Compatibility Specification

The legacy repository structure stored MLflow as:
- **Legacy SQLite DB**: `<root>/.cache/mlflow.db` (standalone file in `.cache/`)
- **Legacy Artifacts**: `<root>/.cache/mlflow_artifacts/` (directory in `.cache/`)

To guarantee zero regression for legacy workflows:
1. `LATENTMAS_USE_LEGACY_MLFLOW_CACHE=1` enables legacy fallback.
2. `PathResolver.legacy_mlflow_db_path` searches both `<root>/.cache/mlflow.db` and any subdirectory variation `<root>/.cache/mlflow/mlflow.db`.
3. `PathResolver.legacy_mlflow_artifacts_dir` searches `<root>/.cache/mlflow_artifacts/` as well as `<root>/.cache/mlflow/mlflow_artifacts/`.
4. When a legacy DB exists but the environment flag is unset, the system logs an informative notice directing the researcher to `docs/migration_plan.md` without silent overwrite.
